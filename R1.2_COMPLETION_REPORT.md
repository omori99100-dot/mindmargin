## 4. Workflow Lifecycle Analysis

### 4.1 Actual call path

The relevant path is:

```text
WorkflowEngine.start()
  → daemon thread _execute_ready()
    → daemon thread _execute_step()
      → handler / timeout wrapper
        → _complete_step() or _fail_step()
          → _save()
            → path.parent.mkdir(...)
            → path.write_text(...)
```

`WorkflowEngine.__init__` derives `self._persist_dir` from a caller-owned `persist_dir` and creates `persist_dir/workflows`. `start()` returns after launching a daemon thread; it does not provide a joinable lifecycle handle to the caller. The unit-test fixture owns a temporary directory and removes it during teardown. This creates a lifetime mismatch: worker threads may still execute `_complete_step`, `_fail_step`, or final `_execute` persistence after the test-owned directory is being removed.

### 4.2 Resource lifecycle evidence

The current `_save()` attempts to recreate the parent directory before writing. That is not a complete ownership boundary because directory creation and file writing are not coordinated with external `shutil.rmtree` cleanup or with all concurrent worker writes. The R1.2 full-suite traceback shows that the defensive recreation itself can raise `FileExistsError` in the worker thread, proving an unhandled race remains in the current path.

### 4.3 Root-cause hypothesis

**Supported hypothesis:** the workflow warning is caused by an unsynchronized lifecycle between daemon worker threads and a temporary directory owned and deleted by the test/request scope, compounded by concurrent worker attempts to persist the same workflow directory. The evidence supports the lifecycle/concurrency class of failure and the exact persistence call path. It does not prove which low-level interleaving occurred in every historical `FileNotFoundError`, so the exact interleaving remains `requires_review`.

### 4.4 Classification

**Workflow temporary-path lifecycle: `requires_review` / deferred-remediation.** It is not resolved. The issue was reproduced as a current `FileExistsError` warning under the full suite, while the historical evidence used `FileNotFoundError`. Both occur at the worker persistence boundary and are consistent with the same unsynchronized resource-lifecycle class.

### 4.5 Proposed remediation — not executed

A future, separately authorized remediation should evaluate worker ownership and completion semantics first: provide a lifecycle-safe join/await contract or a durable worker-owned persistence root, coordinate cleanup with active workers, and make persistence writes atomic and race-safe. Any change to `mindmargin/core/workflows.py`, tests, production workflow behavior, or persistence semantics requires a separate authorization. No such change was made in R1.2.

## 5. SQLite Concurrency Analysis

### 5.1 Actual call path

The growth-analysis path is:

```text
run_growth_analysis()
  → cluster_published_topics() / identify_growth_opportunities() / analyze_portfolio_balance()
    → analytics.memory read helpers
    → expand/persist paths where applicable
  → save_best_practice()
    → _get_db()
    → sqlite connection.execute()
    → commit()
```

`analytics.memory._get_db()` creates one SQLite connection per thread using `threading.local()`, pointing all threads at the same `mindmargin.db`. Each new thread sets WAL mode, a 5000 ms busy timeout, and invokes `_init_schema()`.

The connection layer contains multiple write helpers that execute and commit directly. `save_best_practice()` has a bounded three-attempt retry for lock errors, but other write helpers do not share the same retry policy. Schema initialization includes DDL/ALTER work and cleanup/index operations on first connection setup, which expands the lock surface when multiple threads initialize connections concurrently.

### 5.2 Evidence

Historical R1 evidence recorded:

```text
sqlite3.OperationalError: database is locked
```

The failure occurred in `tests/unit/test_growth_engine.py::TestRunGrowthAnalysis::test_full_analysis` during the first full-suite run. The affected test passed in isolation, a later full suite passed, and the current R1.2 isolated test and full-suite run passed. The current R1.2 run therefore did not reproduce the lock, but the prior failure is concrete evidence and must not be erased by a successful retry.

### 5.3 Root-cause hypothesis

**Partially supported hypothesis:** the historical lock is intermittent and likely arises from concurrent writers or concurrent connection/schema initialization against the shared SQLite file. The thread-local connection model, per-connection schema initialization, multiple direct commit paths, and uneven retry coverage establish a credible locking surface. The exact contending writer and timing were not captured in the historical failure log, so a definitive root cause is not proven.

Environmental/process scheduling factors may influence reproduction, but no claim is made beyond the observed evidence.

### 5.4 Classification

**SQLite locking/concurrency: `requires_review` / deferred-remediation.** It is not resolved. It was not reproduced in the current isolated or full-suite run, but the historical first-run failure is unexplained and a retry alone is insufficient for closure.

### 5.5 Proposed remediation — not executed

A future, separately authorized investigation/remediation should identify all simultaneous writers and schema initializers, establish a single schema-initialization ownership model, define a consistent write serialization/retry policy, and test concurrent full-suite behavior repeatedly. Any change to SQLite architecture, connection management, transaction policy, persistence configuration, or `analytics/memory.py` requires a separate authorization. No such change was made in R1.2.
